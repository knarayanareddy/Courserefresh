# Tool permissions and the human exit

**Learning objective.** By the end you can declare what an agent's tools may touch, prove it by
reading one settings block, and name the exit that brings a human in.

## Declared scope, not vibes
The tools, and their parameters, are declared in `tool_permissions.tools` in the workflow settings.
A model may *ask* for a tool; the runtime refuses anything outside the declared scope. The block is
the contract: if it is not in the settings, it does not exist.

## The three permission models
1. **Allowlist.** Only named tools run. Everything else is a refusal with a reason code.
2. **Human exit.** For irreversible calls (payments, outbound messages, deletes) the workflow waits
   for a human decision; the wait is visible on the execution.
3. **Blanket.** No. A blanket permission turns a prompt injection into a data-loss incident.

## Reading a settings block
```json
{"tool_permissions": {"tools": ["http_request", "apify_run_actor"],
  "parameters": {"http_request": {"allow": ["docs.n8n.io", "docs.apify.com"]}}}}
```
The allowlist above is host-scoped: a redirect to another host is a refusal, not a run.

## Stop conditions (the honest ones)
- No corroboration for a claim that would change behaviour.
- A tool outside the declared scope.
- A learner-facing message without consent on record.

## Practice
Rewrite one workflow you own so that `http_request` is host-scoped, and write the sentence a judge
would ask for: *"here is where it refuses."*
