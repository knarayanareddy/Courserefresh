# n8n fundamentals: nodes, items, executions

**Learning objective.** Explain nodes, items, executions and credentials, how data flows as an item array, and what makes an execution auditable.

## 1. Why n8n, in one paragraph

n8n is a fair, source-available workflow automation platform: workflows are drawn
visually as canvases of nodes, but every node's behavior remains inspectable code
and config, self-hostable and automatable via API. That combination — *visual for
onboarding, inspectable for audits, API-driven for operations* — is why it is the
decision layer of this course. The canvas is not just a drawing; it is the
governance surface on which every decision of your agent runs, records and can be
replayed.

## 2. The four nouns

**Node.** The unit of work: trigger, fetch, transform, decide, write. Each node has
a type (scheduleTrigger, code, httpRequest, github, telegram…), parameters, and —
crucially — a **contract**: what it puts out and what it expects. When we say "the
canvas as a governance surface," we mean you can print the canvas, read every
node's contract, and know the system's behavior without running it.

**Item.** Data flows between nodes as an **array of items** — each item a JSON
object. Most nodes run once per item by default (fan-out semantics). The single
most common n8n performance/safety surprise is forgetting this: a 50-item array
into an LLM node is 50 calls unless you toggle per-node "execute once" batching.
Conceptually, items are your evidence pipeline's carriage: a snapshot row, a claim
object, a receipt.

**Execution.** Every run is recorded: status (success / error / waiting), start
time, per-node input/output data. This is n8n's second superpower after the canvas:
**auditable by default**. The execution log is the runtime's built-in receipt of what
it did. (Pair it: n8n records the run; your system writes the decision receipts on
top — Lecture 16.)

**Credential.** Stored encrypted, referenced by name, and **never appear in
workflow exports**. The separation between canvas and key store means a workflow
JSON can be shared, versioned, and committed to git without ever carrying a secret.
Breaking that separation (Chapter 9's env-var pattern) is the closest thing to a
sin in n8n operations.

## 3. Reading an execution like an operator

Given any n8n execution, extract the operational story in four steps:
1. **Status and duration.** success at 03:02–03:04 → a clean pulse of the loop.
2. **Trigger item.** Which trigger fired, and with what input — a schedule tick, a
   webhook post from the scan, an error trigger from a sibling workflow.
3. **Per-node I/O.** Walk the canvas in data-flow order and read each node's input
   and output items. The first node whose output surprises you is your incident.
4. **The receipt underneath.** A clean production system writes one decision
   receipt per decision, cross-referencing the execution id, so the n8n execution
   log and the receipt chain tell one story.

```
execution 8fA2 …  wf-cr-1-triage        03:02:41 → 03:02:47  SUCCESS
  n1 webhook        in:  {event_id: cr-n8n-rename-01, …}
  n2 BUILD_PROMPT   out: {prompt_id: P-03, snapshot_refs: 3}
  n3 OBSERVE (LLM)  out: {claims: 1, candidate: "1.85 renames …"}
  n4 ANCHOR_QUOTES  out: {quote: "The tool-permission setting is now …", span: [412-481]}
  n5 JUDGE (LLM)    out: {materiality: material_breaking, sources_verified: 2, …}
  n6 POLICY         out: {action: PUBLISH, reasonCodes: ["material_breaking"], authority: PA2}
  n7 RECEIPT        out: {receipt_id: rcpt-26-793-000, prev: rcpt-…-009}
```

Reading tip: don't read top to bottom passively — hunt for the divergence between
what you expected and what each node emitted. The node where those diverge is the
phase (Lecture 01's vocabulary) where your loop misbehaved.

## 4. Subworkflows and the error contract

Workflows compose: the scan calls triage via webhook; triage calls act. Sub-workflow
architecture mirrors the loop phases one-to-one (`wf-cr-0-scan` → `wf-cr-1-triage` →
`wf-cr-2-act`, plus `wf-cr-3-learn`, `wf-cr-4-digest`, `wf-cr-9-errors` as the
always-attached safety net — Lecture 08). Two contract rules when composing:

1. **Pass contracts, not vibes.** The webhook payload between two workflows is a
   schema: `event_id`, `claim`, `quotes`, `sources[]`. Validate at the boundary
   (Lecture 07's guard pattern), refuse early and loudly.
2. **Errors travel upward.** A subworkflow's throw must surface in the parent as
   data (via the error workflow), never evaporate into a "partial" state that looks
   like success from outside.

## 5. Common mistakes

1. **Item fan-out surprise.** N items → expensive node → N bills. Toggle batch/execute-once strategically; know which nodes are per-item by default.
2. **Siloed executions.** n8n's log proves the *run*; it does not interpret the
   *decision*. Ship receipts on top (why: Lecture 16).
3. **Drag-and-drop without contracts.** A node without a written contract is a
   future CVE with a nice icon.

## Recap and practice

You can define node/item/execution/credential, read an execution like an operator,
and reason about fan-out semantics.
