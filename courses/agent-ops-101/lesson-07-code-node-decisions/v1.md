# The Code node: deterministic decisions on the canvas

**Learning objective.** Write a Code-node rule block that decides deterministically with no model call inside it, and explain why the decision belongs in code while the model only proposes.

## 1. The most important box on the canvas

If you remember one node from this course, remember this one. The Code node is a
plain JavaScript sandbox on the canvas. Courserefresh's POLICY node — the decision
maker of the entire system — is a Code node of about a hundred lines. No model call,
no network, no nondeterminism: **the same inputs always produce the same action and
reason codes.** That property is why the decision layer can be tested in CI,
replayed, and trusted to run at 03:00 without supervision.

The design rule this lecture exists to teach:

> **Models propose. Code disposes.**
> The LLM observes evidence and answers closed questions; the Code node takes those
> answers and *decides*. Never the reverse. Never mixed.

Why so absolute? Because a decision made by a model is a decision made by a
probability distribution: it cannot be unit-tested, it drifts with model versions,
it cannot be reproduced in an incident post-mortem ("why did it publish?" — "the
model felt 0.73 about it"), and it silently changes when the vendor updates the
model. A decision made by code is none of those things. The whole accountability
architecture of the course — receipts, parity tests, revert gates — presupposes
deterministic decisions.

## 2. The shape of a policy block

Here is the canonical skeleton (the real one is Lecture 15):

```javascript
// POLICY — ordered rules, first match wins. No model calls inside.
const inp = $input.first().json;            // the DecisionInput
const out = (action, codes, extra = {}) => ({
  action, reason_codes: codes,
  authority: inp.authority, decided_by: "policy-node",
  execution_id: $execution.id, prev_receipt: inp.prev_receipt_id,
  ...extra,
});

// Safety rules first — a hostile page cannot be rescued later.
if (inp.injection_score >= 0.5)  return out("ESCALATE",  ["injection_or_jailbreak"]);
if (inp.sources_verified < 2)    return out("ESCALATE",  ["insufficient_corroboration"]);
if (inp.source_conflict)         return out("ESCALATE",  ["source_conflict"]);
if (inp.assessment_touched)      return out("ESCALATE",  ["assessment_integrity"]);   // PA3 forever
if (inp.budget_exceeded)         return out("ESCALATE",  ["over_budget"]);
if (inp.materiality === "cosmetic" || inp.materiality === "marketing_noise")
                                 return out("NO_CHANGE", ["below_materiality"]);
if (inp.action_requested === "REVERT" && !inp.gate) return out("ESCALATE", ["gate_missing"]);
return out("PUBLISH", ["corroborated_change"]);       // R8: the default is earned
```

Read it as an argument, because it is one: *given everything the verify phase
established, what is the only defensible next action?* The order is the argument's
structure — safety before economy before action — and "first match wins" means any
reader can simulate the block by hand with a pencil, which is precisely what a
reviewer, a judge, or a post-mortem needs to do.

## 3. Contracts in, contracts out

A Code node is only as deterministic as its inputs are disciplined. Two contract
habits keep it that way:

**Validate at the boundary.** The first lines destructure and *check* the input
schema; unknown keys are not passed through silently:

```javascript
const need = ["injection_score","sources_verified","materiality","authority","prev_receipt_id"];
const missing = need.filter(k => inp[k] === undefined);
if (missing.length) return out("ESCALATE", ["unknown_state"], { missing });
```

Unknown state fails **closed** — escalate, don't guess. This is the same "fail to
the safe action" posture as Lecture 04's stop conditions, applied to plumbing.

**Emit a closed vocabulary.** The output uses a fixed set of actions
(`PUBLISH|ESCALATE|NO_CHANGE|DISPATCH|REVERT`) and reason codes from a published
taxonomy. Downstream nodes branch on enums, never on prose. A policy that can emit
"maybe publish?" has already failed its contract.

## 4. Determinism in practice: pure functions + named version

Three habits make the block *provably* deterministic rather than *aspirationally*:

1. **Pure function of the input.** Everything the block needs arrives in the
   DecisionInput — no reads of global state, no `Date.now()` inside the decision
   (timestamps are added by the receipt writer, outside), no random. Same input,
   same output, forever.
2. **No I/O inside the decision.** Network or DB calls would smuggle
   nondeterminism back in (and stall the canvas). The policy decides; other nodes do.
3. **Version the rules.** The rules text is itself an artifact with a hash — the
   receipt records `policy_sha`. When R6's threshold moved 0.45→0.52 after a panel
   review, every receipt after that change named a different policy hash. You
   cannot audit what you cannot version.

## 5. Common mistakes

1. **The model in the middle.** "Let the LLM look at the judge scores and decide
   the action." That sentence reintroduces every property we removed. The model
   supplies the *scores*; the block compares them to thresholds.
2. **Rules out of order.** Putting `assessment_touched` after materiality means a
   graded-quiz rewrite rolls on down to "publish" because it was also material.
   Order is semantics (Lecture 15 drills this until it's reflex).
3. **Open-vocabulary outputs.** Any downstream node forced to `includes("publish")`
   is matching vibes. Enums only.
4. **Silent catch-alls.** A final `return PUBLISH` with no reason code makes the
   default invisible in receipts. Every branch — especially the default — carries
   its reason.

## Recap and practice

You can write a policy block skeleton, validate inputs, emit closed vocabularies,
and defend "models propose, code disposes" in one sentence. 

**Practice:** (a) Add an `over-escalation` guard: a rule that turns a NO_CHANGE
into a DRAFT when confidence < 0.6 — where does it go in the order, and why?
*(After safety, before materiality default — it must not shadow R1–R5 refusal
semantics but must qualify the publish/decline axis.)* (b) Write the three-line
version of YOUR capstone's policy — the three rules that would stop the line for
you — and we expand it into R1–R8 form in Lecture 15's lab.
