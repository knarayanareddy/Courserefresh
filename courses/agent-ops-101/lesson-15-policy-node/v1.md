# The POLICY node: ordered rules, first match wins

**Learning objective.** Order the policy rules R1–R8 and predict the action for a given input; explain parity testing — the same rules in two runtimes with zero disagreements allowed.

## 1. The rulebook, in full

Lecture 07 built the skeleton; this is the complete rulebook as it runs in
production, and the order is the argument:

```
R1  injection_score >= 0.5                → ESCALATE [injection_or_jailbreak]
R2  sources_verified < 2                  → ESCALATE [insufficient_corroboration]
R3  source_conflict                       → ESCALATE [source_conflict]
R4  assessment_touched                    → ESCALATE [assessment_integrity]   // PA3 forever
R5  budget_exceeded                       → ESCALATE [over_budget]
R6  materiality ∈ {cosmetic, marketing_noise}
                                          → NO_CHANGE [below_materiality]
R7  action_requested = REVERT ∧ ¬gate     → ESCALATE [gate_missing]
R8  default                               → PUBLISH [corroborated_change]
```

**First match wins.** Simulate it with a pencil: take the DecisionInput, walk from
R1, stop at the first true predicate. The order encodes a priority argument worth
being able to recite — safety outranks corroboration, corroboration outranks
economy, and irreversibility outranks everything:

1. **R1 before everything:** a hostile page cannot be rescued by good
   corroboration later in the list; suspicion is raised, never lowered.
2. **R2/R3 before economy:** under-corroboration and conflict are evidence
   problems; they disqualify before cost questions arise.
3. **R4 is absolute:** grading-adjacent changes never ride a good-evidence
   default to publish — no rung of the ladder unlocks R4's territory (Lecture 02
   PA3-forever).
4. **R5 stops the meter:** an over-budget loop escalates rather than publishing
   its way past the cap.
5. **R6 is the respect rule:** cosmetic changes *correctly* produce no action —
   churn is a cost the rulebook refuses to pay. (When the materiality threshold
   moved 0.45→0.52 after panel review, three gold rows flipped PUBLISH→NO_CHANGE —
   the threshold is a versioned, receipted artifact, not folklore.)
6. **R7 forbids und gate reverts:** reverting is an *earned* action — the gate
   must have fired per its written contract, or the revert itself needs a human.
7. **R8 is earned by elimination:** the publish default is not optimism; it is
   what remains when every refusal rule had its chance to say no. That is why
   its reason code is `corroborated_change` — the default *names its evidence*.
8. **Authority multiplies the verdict:** the final action is intersected with the
   current authority level (a PUBLISH at PA0 is a DRAFT; a notify at PA1 stages
   no cards). The ladder is applied *inside* the policy, not bolted on after.

## 2. Reasons are a closed taxonomy

Every rule emits reason codes from a published, closed taxonomy —
`injection_or_jailbreak`, `insufficient_corroboration`, `source_conflict`,
`assessment_integrity`, `over_budget`, `below_materiality`, `gate_missing`,
`corroborated_change`, `stuck_signals_met`, `consent_missing`, `rate_limited`,
`human_signoff`, `revert_gate_satisfied`, `duplicate_suppressed`, `unknown_state` —
and the receipt records them all. Closed means: digest sections aggregate by code,
tests assert exact codes, and a new code is a *policy amendment* (versioned,
hashed, reviewed), not a string somebody typed.

## 3. Parity: the same rules, two runtimes, zero disagreements

The single most distinctive engineering artifact in this architecture: **the
rulebook runs in two places**, and the build breaks if they ever disagree.

- **Production:** `app/n8n/policy_node.js` — JavaScript, inside the n8n Code node,
  on the canvas.
- **Oracle:** `specs/courserefresh/skin/policy.py` — Python, in the test harness.

Both are fed the same **gold set**: ≥40 labelled DecisionInputs with expected
actions and reason codes (`gold.jsonl`, versioned and hashed itself — Lecture 21
covers the labelling protocol). The parity test runs every row through both
implementations and requires `action match rate = 1.000` and identical reason
codes. The running repo exports 59 rows plus two probe rows; the report prints
`action match 1.000` or the build stops.

What parity buys, concretely:

1. **The canvas is provably the decision maker.** Not "the same logic, we
   believe" — the same rows, bit-for-bit, through both runtimes. When the demo
   says "n8n decides," the receipt carries `canvas.execution_id` and parity is
   the reason to believe it.
2. **The oracle keeps production honest.** A hotfix to the JS rules whose Python
   mirror is forgotten fails CI within minutes — the rulebook cannot drift
   between what runs and what tests.
3. **The offline twin is *not* a mock.** When the canvas is down, the twin
   decides by the same rules and is *labelled* OFFLINE TWIN (Lecture 08). Judge
   an incident or a demo on the twin's receipts with the same confidence the
   labels allow.

The parity discipline extends to any second consumer of the rules: add a rule →
add it to BOTH mirrors → add gold rows that exercise it → run the parity test →
release. Four steps, no exceptions, and the receipt history shows the discipline
held through threshold changes and rule additions.

## 4. Reading policy receipts fluently

The receipt is the rulebook's voice after the fact. Read one:

```
rcpt-26-793-000 · PUBLISH · [corroborated_change] · authority PA2 · decided_by policy-node
inputs:   materiality=material_breaking · sources_verified=2 · injection=0.02 ·
          conflict=false · assessment=false · budget=18.4/25 · gate=armed
policy:   sha256:9c1f… (v0.3) · rules evaluated: R1✗ R2✗ R3✗ R4✗ R5✗ R6✗ R7✗ → R8
artifact: lesson-04 v3→v4 · diff_hash 2ba669… · quiz q2 regenerated
canvas:   execution_id 8fA2… · prev rcpt-26-793-009
```

The `rules evaluated` line is parity in miniature: any reader can replay R1–R7 by
hand from the inputs row and land on R8 — the receipt *teaches its own decision*.
Post-mortems stop being arguments about intent and become reading exercises.

## 4b. A worked trace, rule by rule

```
in:  materiality=material_breaking · sources_verified=1 · injection=0.02
     conflict=false · assessment=false · budget=3/25 · action_requested=PUBLISH
R1?  0.02 < 0.5 ……………………………………………… R1 no
R2?  sources_verified=1 < 2 ……… R2 FIRES
→ ESCALATE [insufficient_corroboration] · claim preserved for the human
```

Compare with the same input at `sources_verified=2`: R1–R7 all fall through, R8
publishes with `[corroborated_change]`. One predicate of difference, two receipts,
two different worlds — that is the whole policy in one breath, and the pencil-
simulation drill from §1 is how you make it reflex.

## 5. Common mistakes

1. **Reordering "for efficiency."** Moving R6 before R4 lets a cosmetic-but-
   assessment-touching change NO_CHANGE its way past the PA3 wall. Order is
   semantics; it is never a performance question.
2. **One runtime, vibes for the other.** "The Python is basically the same" —
   parity exists because "basically" is where incidents live. Zero disagreements
   is a floor, not a stretch goal.
3. **Open reason codes.** A bespoke `"kind_of_dubious"` code breaks digest
   aggregation and every test that asserts codes. Taxonomy changes are
   amendments.
4. **Dismissing the default's reason.** `corroborated_change` on R8 output is not
   decoration: it asserts the conditions every refusal rule checked and passed.
   A default without its reason is unaccountable optimism.

## Recap and practice

You can recite R1–R8 with the priority argument, simulate any input by hand, read
the `rules evaluated` line, and explain what parity proves about the canvas.

**Practice (the pencil drill, all three):**
1. `injection=0.93, sources_verified=2, materiality=material_breaking` → 
   *(R1 fires: ESCALATE [injection_or_jailbreak]. Good corroboration of a hostile
   page is still a hostile page.)*
2. `injection=0.02, sources_verified=2, conflict=true, materiality=material_breaking` →
   *(R3 fires — before R4–R8 are even consulted. Conflict → human.)*
3. `injection=0.02, sources_verified=2, materiality=cosmetic, budget=24/25` →
   *(R5 no budget problem — 24/25 not exceeded; R6 fires: NO_CHANGE
   [below_materiality]. A change that "merely" rewords is correctly refused.)*
