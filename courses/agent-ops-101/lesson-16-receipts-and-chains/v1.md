# Receipts, diffs & hash-chained memory

**Learning objective.** Read a receipt: input, decision, reason codes, preserved quotes, artifact hashes; explain how a hash chain makes an action arguable after the fact — and what verify_chain proves.

## 1. The receipt: one decision, one row, everything

A receipt is the atomic unit of accountability: **every decision — publish,
refusal, dispatch, signoff, error — writes exactly one append-only record**, and
every record carries enough to reconstruct and dispute the decision without the
system's help:

```
{ "receipt_id": "rcpt-26-793-000",
  "ts": "2026-09-26T17:26:16Z",
  "run_id": "cr-20260926-1726-793",
  "event_id": "cr-n8n-rename-01",
  "mode": "sim",                       // live · sim · degraded — always labelled
  "decision": {
    "action": "PUBLISH",
    "reason_codes": ["corroborated_change"],
    "authority": "PA2",
    "decided_by": "policy-node"
  },
  "inputs": {                          // the full DecisionInput, verbatim
    "materiality": "material_breaking", "sources_verified": 2,
    "injection_score": 0.02, "quotes": ["The tool-permission setting is now …"],
    "policy_sha": "9c1f…", "gate": {"metric": "quiz_delta", "condition": "<= 0",
                                     "n_min": 5, "window_h": 48}
  },
  "artifact": {                        // what the action did — or would have
    "lesson_id": "lesson-04-tool-permissions", "from": "v3", "to": "v4",
    "diff_hash": "2ba669…", "quiz_regen": "q2"
  },
  "prev": "rcpt-26-793-009:key:5f2…"   // chain link — see §3
}
```

Three design rules make receipts worth their bytes:

1. **Inputs verbatim, not summarised.** The receipt records the full DecisionInput
   — the quotes *as anchored*, the scores as scored, the policy hash as running. A
   summarised input is a paraphrase, and paraphrases are the enemy of
   arguability.
2. **Refusals are first-class.** An ESCALATE receipt preserves the claim and its
   quote even though nothing was published — *especially* because nothing was
   published. The human reviewing the escalation needs the exact evidence, and
   the digest aggregates refusals by their reason codes.
3. **The receipt precedes the action.** For writes, the receipt is written before
   (or atomically with) the artifact; an action without its receipt is a defect
   the chain check catches. Contrast with "we logged it after, if we remembered."
    Receipt coverage — decisions with receipts / decisions — is a contract-tested
   **100%**, not a best-effort percentage.

## 2. Diffs: the action's face

The artifact section names versions (`v3 → v4`) and the diff hash; the diff file
itself (`diffs/v4.diff`) is the human-readable face of the action. Rules:
**every** publish writes a new version — no in-place edits (Lecture 03); the diff
is computed and hashed at write time (the hash into the receipt prevents
after-the-fact diff tampering); and reverts are versions too — v5 restoring v3 is
*a new version with its own receipt and diff*, not a magical undo (Lecture 18).
The changelog row ties receipt, diff and motivation together in the course's
public history.

## 3. The chain: hash-linked receipts

Receipts link: each carries `prev: <prior receipt id + hash>`. The result is a
tamper-evident log — the same construction as a blockchain's spine, minus the
ceremony:

```
genesis → r-000 → r-001 → r-002 → … → r-008   (the hero run's 9 rows)
             │        │        │
             └─ verify_chain() recomputes each link hash and
                checks: no gaps, no rewrites, no insertions
```

**What the chain proves — and what it does not.** `verify_chain() == true` at run
end proves the *log's integrity*: every receipt is still exactly what the system
wrote, in the order it wrote it, since genesis. It does **not** prove the
decisions were *right* (that is what the eval's gold rows are for) — it proves
nobody edited history. The distinction matters and is worth reciting: **the chain
is memory integrity; the gold set is decision quality.** Together they make an
action *arguable*: "here is exactly what was decided, on exactly what evidence,
and here is a labelled suite proving the decision rule."

The attack model makes the design concrete: with an append-only plain log, an
intruder (or a well-meaning colleague) can rewrite Saturday's receipt to hide a
bad publish; the next `verify_chain()` fails at the broken link and the digest
names the gap. Silence is defeated structurally — which is why **chain integrity
is a run-end contract**: every cycle ends with the check, and the digest prints
it (`chain ✓ 9 rows`), so even the *checker's* absence is visible on the one page
the operator reads.

## 4. Reading the chain in an incident

The post-incident drill (lab 16 runs it end to end):

1. **Anchor at the artifact.** Start from the world — the lesson version, the
   diff — and find the receipt naming its hash.
2. **Walk backward.** Each receipt names its predecessor; inputs quote
   snapshots; snapshot hashes open files. Every hop is verifiable because every
   hop is a hash.
3. **Replay the policy.** The `inputs` row + the policy hash replay the decision
   by hand (Lecture 15's pencil drill). If the replay disagrees with the
   recorded action, *the incident is in the policy*, and the policy version is
   pinned in the receipt.
4. **Read the mode labels.** A sim receipt must never masquerade as live; the
   label rides every row, and the honest post-mortem names it.

Four hops: world → receipt → evidence → rules. No step trusts memory, a colleague's
recollection, or the system's own current state — only hashes and files.

## 5. Common mistakes

1. **Logging after the fact.** "We'll write the receipt in the digest pass."
   Between action and log lies a window where the system did something
   unaccounted. Write first, act on the receipt's tail.
2. **Summarised inputs.** Compact receipts are beguiling and useless in disputes.
   Verbatim inputs (with anchored quotes) are the entire point.
3. **Unhashable artifacts.** A receipt naming `diff_hash` nobody can recompute —
   or a snapshot the receipt doesn't address — breaks the verification grammar.
   Every artifact reference is a hash address, or it is a description.
4. **Chains without checks.** The chain that nobody verifies is a ritual.
   `verify_chain()` at run end, printed in the digest, tested in CI — or don't
   bother linking.
5. **The receipt as self-praise.** Logs that say "successfully updated the
   lesson!" are marketing. Receipts carry inputs and decisions; interpretation
   belongs to the digest and the humans.

## Recap and practice

You can read a receipt's five sections, follow the chain links, and run the
four-hop incident drill; you can state precisely what verify_chain does and does
not prove.

**Practice:** (a) In the receipt above, the gate is recorded inside `inputs` — why
must the gate live in the receipt rather than "in the system"? *(Because
Lecture 18's revert is *evidenced* by the gate that was recorded at publish
time; a gate that lives only in current state can be edited to match the outcome
it wants.)* (b) For your capstone, define the five receipt sections in one line
each — then write the Chain test: how exactly does your `verify_chain()` fail
when someone edits a middle row? Saying "it hashes differently" is the start;
trace which link breaks and what the digest prints.
