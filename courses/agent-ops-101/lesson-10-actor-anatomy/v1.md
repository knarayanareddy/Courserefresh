# Actors, datasets & key-value stores

**Learning objective.** Describe an actor's input schema, dataset, key-value store and run log, and say what a dataset row must minimally contain to be usable as evidence downstream.

## 1. The industrialised fetch

Lecture 09 bounded individual HTTP calls. But "fetch a real web page reliably" is
not one call: it is TLS negotiation, redirect following, JavaScript rendering,
session management, proxy rotation, retry queues, and structured output — a
sub-industry of engineering that fails in creative ways (L4 → 403s, geo-blocks,
headless-browser footprints). **Apify actors** industrialise exactly this: an actor
is a packaged, parameterised fetch program running on Apify's infrastructure, with
proxies, retries and browser rendering managed for you.

The course's running case study uses `apify/website-content-crawler` (pinned to
build `0.3.97`, id `u8gClHFAIyDHCQq0J`) for every source. Same actor, different
inputs — because actors are *programs*, and programs take parameters.

## 2. The four organs

**Input schema.** An actor declares a JSON Schema — the parameters a run accepts
and their types (`startUrls`, `maxPages`, `crawlerType`, `proxy`). Inputs are
**validated against the schema before the run starts**: garbage in, rejected at
the door, not three pages into the crawl. (Apify tightened this contract — schema
validation before run start — and the running case study receipts the change.)
Your JSON stays in your config, versioned; the actor contract is the boundary.

```
{ "startUrls": [{"url": "https://github.com/n8n-io/n8n/releases"}],
  "maxPages": 5,
  "crawlerType": "cheerio",
  "proxy": {"useApifyProxy": true} }
```

**Dataset.** The actor's structured output: an append-only store of JSON rows, one
per result item — for a content crawler, one per fetched page: `url`, `markdown`
(the extracted text), metadata fields. Datasets page at 1,000 items (Lecture 11's
paging), and every row is addressable forever after the run. **The dataset is the
evidence pipeline's conveyer belt**: all downstream verification, claims and
receipts start from dataset rows.

**Key-value store.** Arbitrary binary artefacts: screenshots, raw HTML snapshots,
PDFs. Where the dataset is schema-shaped, the KV store is blob-shaped. Use it for
the *raw evidence* a dispute might need later — the screenshot of the page as
fetched — while the dataset carries the parsed rows you actually process.

**Run log.** The timestamped stdout of the run — every fetch, proxy decision, and
warning, visible in the Apify console and via API. This is your fetch-layer
execution log: when a source looks wrong, the run log is where you find out whether
the fetch misbehaved or the page did.

## 3. What a dataset row must carry to be evidence

Not any row will do. For a row to participate in the verify→decide→receipt chain
downstream, it must carry at minimum:

| Field | Why it exists |
|-------|---------------|
| `url` | Provenance — the claim's address. Without it there is nothing to re-visit |
| `markdown` (or equivalent extracted content) | The claim's substance — what ANCHOR_QUOTES will quote from |
| fetch metadata (timestamp, status) | When the world was seen, and whether the fetch was healthy |

Rows failing the required-fields check don't travel: the normalize step drops
them to a `parse_failed` error receipt (Lecture 08), not into a claim. **Evidence
that cannot name its provenance is not evidence** — it is content that happens to
exist. The config declares two required fields (`url`, `markdown`) for every
source; the contract is explicit, checked, and cheap.

The deepest property of this layer is **reproducibility**: run id + build tag +
input + dataset = a fetch you can re-derive later. When a judge challenges "are
these real pages?", the answer is run history, input JSON, and the pinned build —
checkable, not asserted.

## 4. Choosing and taming an actor

Actor-store reality: hundreds of actors, uneven quality. A short due-diligence
list (use it in the capstone):

1. **Does its output match your downstream contract?** Look at the input schema
   and a sample dataset *before* committing the pipeline shape.
2. **Is it maintained?** Recent builds, issue activity. Abandoned actors rot like
   abandoned libraries.
3. **Can you pin it?** You need a build number, not a floating tag (Lecture 11
   exists because of this).
4. **What does it cost?** Actor compute is metered (per-run or per-unit pricing);
   estimate against your cadence arithmetic (Lecture 06).
5. **Trust boundary.** Actors are third-party code fetching third-party content.
   Treat output as untrusted input all the way down — injection lives here
   (Lecture 04), and the KV-store raw snapshot is the memory of what was actually
   served.

## 5. Common mistakes

1. **Trusting extraction.** `markdown` from a crawler is *someone's parse of
   someone's page*. It carries the full trust boundary of untrusted input — never
   executes, never gets templated into prompts unquoted.
2. **Unpinned actors.** `latest` in production: builds change under you, output
   shapes shift (a new `metadata.statusCode` field arrives and your transform
   throws on unexpected keys). Lecture 11 formalises the fix.
3. **Dataset as dumping ground.** Rows without the required fields dilute the
   evidence pipeline. Validate at the normalize boundary; fail loudly, early.

## Recap and practice

You can describe the four organs, name the required evidence fields, and audit an
actor choice against a five-point due-diligence list.

**Practice:** for your capstone subject, write the input JSON for one source's
crawl (URL, page cap, crawler type, proxy) and the required-fields contract for
its dataset rows. Then answer: if a row arrives empty of content but with a URL,
which failure path does it take, and what does the receipt say? *(parse_failed →
error receipt: input preserved, digest line staged, no claim, nothing published.)*
