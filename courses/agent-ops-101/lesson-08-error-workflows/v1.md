# Error workflows: a crash is never silence

**Learning objective.** Attach an error workflow to a production workflow, describe its payload, and show how a thrown error becomes a receipt and a digest line instead of silence.

## 1. The failure that looks like success

Of the four failure species (Lecture 04), **silence** is the deadliest, because
from the outside it is indistinguishable from a quiet night. A workflow throws at
04:10 — the actor timed out, the judge endpoint 500'd, a code node hit an
unexpected key. The execution stops. Nothing is published, nothing is said, the
digest at 07:30 reads "no changes" — which is technically true and operationally
a lie, because "no changes because nothing changed" and "no changes because the
loop is broken" print identically unless you make them not.

The invariant this lecture installs:

> **A crash is never silence.** Any throw, anywhere, becomes (1) an error receipt
> and (2) a line in the next digest. If the crash was total, the *absence* of the
> digest itself must be noticeable (your watchdog, L14's pause switch, or a
> colleague).

## 2. The mechanism: errorTrigger → receipt

n8n's error workflow is a workflow whose first node is an **errorTrigger**, attached
to sibling workflows via their workflow settings. When any sibling throws, n8n calls
the error workflow with a structured payload — the failing workflow's name and id,
the execution URL/id, the failing node's name and type, the error message, and the
item that was being processed. `wf-cr-9-errors` (five nodes) turns that payload into
accountability in three moves:

```
ERROR TRIGGER          n8n hands us: workflow, execution id, node, message, item
   │
BUILD_RECEIPT (code)   normalise to the receipt schema; classify the error class
   │                   (fetch_failed · judge_failed · write_failed · parse_failed);
   │                   preserve the input verbatim — the hostile input IS evidence
APPEND_RECEIPT  →  receipts.jsonl   (hash-chained like every other receipt)
DIGEST_LINE     →  a pre-staged digest line: "[degraded] fetch failed at 04:10 …"
```

The output is the same artifact family as every other receipt — same chain, same
verification, same first-class citizenship in the digest's refusals-first ordering.
That is the deep point: **errors are not second-class events.** A degraded night
and a productive night leave equally checkable records.

## 3. Degradation, labelled

When a failure degrades capability, the labelling continues everywhere the
degraded data appears:

| Situation | Label |
|-----------|-------|
| Actor run fails → fixtures served instead | `DEGRADED` + the snapshot hash the fixtures stand in for |
| Judge endpoint down → offline twin decides | `OFFLINE TWIN` — same rules (parity-tested), named runtime |
| Live fetches blocked (sandbox) | `SIM` mode on every artifact, run header, digest header |
| Write fails (commit rejected) | error receipt with `write_failed` + preserved diff; digest "the write failed at 04:10; it refused, said why, and the chain still verifies." |

The design test from Lecture 04 recurs here: **a degraded mode presented as healthy
is a lie with uptime.** An operator who reads `mode: sim` knows exactly what
numbers may be trusted and which are declared `unmeasured`. The labels are not
apologetics — they are the interface between the system and its operator's trust.

## 4. Designing your own error path

Four rules, in order of importance:

1. **Attach one error workflow to every production workflow.** Non-optional. If
   the sibling can throw, it has an error contract.
2. **Preserve the input.** The item that triggered the failure is the most
   valuable thing in the payload — for a parse failure it *is* the bug report.
   Log it verbatim inside the receipt (sanitised of secrets, never of substance).
3. **Classify errors into a closed set.** fetch/judge/write/parse + unknown.
   Downstream, "unknown" escalates to a human; the rest route to their recovery
   paths. Open-ended error text is unusable at 07:30; a four-word class is.
4. **Stage the digest line at failure time**, not at digest time. The digest
   builder reads pre-staged lines; nothing about a 04:10 failure depends on the
   07:30 builder being healthy.

## 5. When the error workflow itself fails

Trust, but verify the verifier. The error workflow can also throw (it calls HTTP
nodes too). Two backstops:

- **Chaos-test it.** The course's repo ships a chaos mode that makes the artifact
  write fail on purpose and asserts the failure still produces a receipt. Run
  equivalent drills in your capstone: break one thing per drill (actor, judge,
  write) and read the digest the next morning. If the drill's failure is silent,
  the drill found a real defect.
- **The external watchdog.** Something *outside* the loop watches heartbeats and
  escalates their absence (as this repo's gateway watchdog pattern does for its
  messaging). The digest's own absence must fail loudly too — "digest missing" is
  itself an alert condition.

## Recap and practice

You can attach error workflows, read their payload, build the receipt path, and
label degradation honestly.

**Practice:** (a) Write the receipt your error workflow should emit for a judge
endpoint 500 mid-triage. *(action ESCALATE — no wait, errors aren't decisions:
the receipt class is `judge_failed`, input preserved, degraded line staged — the
distinction matters and is Quiz 4.)* (b) Design the chaos drill for your capstone
that proves "write failure → digest line, not silence."
