# What is agent operations?

**Learning objective.** Define agent operations, name the six loop phases, and state the one question every operator of an autonomous system must be able to answer.

## 1. Why this lecture exists

Most software does what it is told, when it is told. A cron job runs at 03:00; a API
endpoint answers when called; a pipeline transforms what it is handed. None of it
*chooses*. The moment a system chooses its own next action — decides, on evidence it
gathered itself, to do something you did not explicitly command at that moment — you
have left the world of automation and entered the world of **agents**. And with them,
a new engineering discipline: **agent operations**, the practice of running systems
that act while you are not watching, such that you can still trust them on Monday
morning.

This course teaches that discipline with two tools and one running case study.
The tools are **n8n** (the workflow automation platform that will host our decision
logic) and **Apify** (the actor platform that will fetch the real-world data). The
case study is **Courserefresh**: a system that keeps a technical course true as its
subject moves. Every concept in this course is grounded in something that system
actually does — you will read its receipts, walk its canvases, and in the capstone
build its twin for a subject of your own.

## 2. The test: does the system choose?

Draw the line precisely, because the word "agent" is used loosely in the industry.
Apply this test:

> **A system is an agent on the dimension where it chooses its own next action from
> evidence it gathered itself.**

A vending machine does not choose. A cron job does not choose. A support chatbot
answers but chooses nothing that touches the world. But a system that *scans release
notes, judges whether a course lesson is now wrong, and decides to rewrite it* —
that chooses. The test is not intelligence; it is **who initiates the action**. Once
the answer is "the system did, unprompted," every remaining lecture applies to you.

Note the middle case: a **copilot** suggests, a human clicks. Copilots are fine
products and much easier to operate — the human is the safety mechanism. This course
is about the systems where the human is *not* in the loop at action time, because
that is where the interesting engineering lives.

## 3. The loop: notice, verify, decide, act, learn, report

Every trustworthy autonomous system you will ever meet is a variation of one shape —
a loop:

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌────────┐│
   │ NOTICE  │──▶│ VERIFY  │──▶│ DECIDE  │──▶│  ACT   ││
   └─────────┘   └─────────┘   └─────────┘   └────────┘│
        ▲              │             │              │  │
        │              ▼             ▼              ▼  │
        │         ┌─────────────────────────────┐      │
        │         │   LEARN         REPORT      │◀─────┘
        └─────────────────────────────┘◀── the world moved; start again ─┘
```

| Phase | The system… | The artifact it leaves |
|-------|-------------|------------------------|
| **NOTICE** | Fetches the world on a schedule — whether or not anyone is watching | A hashed snapshot of what it saw |
| **VERIFY** | Checks the evidence: how many independent voices? do the quotes support the claim? | Anchored quotes, source roles |
| **DECIDE** | Applies deterministic rules to choose one action from a closed set | A receipt with reason codes |
| **ACT** | Writes the versioned artifact, notifies the consenting humans | A diff, a changelog, a learner card |
| **LEARN** | Watches whether the action helped; keeps the promise to undo | Gate states, micro-lesson dispatches |
| **REPORT** | Says what it did, refusals first | The digest |

Memorise the loop. Every component in this course plugs into exactly one phase, and
when something goes wrong in production, the first diagnostic question is *"which
phase misbehaved?"* The second is *"where is the artifact?"* — because in a
well-operated system, every phase leaves evidence behind.

## 4. The operator's question

Run this thought experiment. Your system ran all weekend: it scanned, it decided, it
acted. On Monday you walk in. What is the one question you must be able to answer?

> **"What did it do while nobody was watching?"**

Not "is it working?" — a system can be busily working at the wrong thing. The
question demands an *account* — an itemised, checkable record of every decision and
action. If your answer is "let me check the logs and reconstruct what probably
happened," you do not have an operated system; you have an unsupervised one. The
entire second half of this course (receipts, receipts chains, digests, evals) exists
to make the Monday question answerable with a document, not an investigation.

Courserefresh answers it with a 4 KB digest that arrives at 07:30 every morning and
lists, before anything else, what the system **refused** to do. We will learn why
refusals come first in Lecture 22.

## 5. Common mistakes (seen in every cohort)

1. **Building the brain before the loop.** Novices start with the model prompt. The
   professionals start with the loop: what is noticed, what is verified, what is
   left behind. The intelligence is the smallest part.
2. **Confusing "autonomous" with "unaccountable."** Autonomy without receipts is
   not a product; it is a liability with a demo.
3. **Optimising the happy path.** The happy path is the demo. Production is what
   happens on the other 364 days — the hostile page, the dead source, the
   over-budget run. We design for those first.
