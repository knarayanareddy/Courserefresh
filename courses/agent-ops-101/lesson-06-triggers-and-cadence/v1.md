# Triggers, schedules & idempotence

**Learning objective.** Choose between schedule, webhook and error triggers for a given job, and explain why content-hash dedupe is required before a schedule can be trusted.

## 1. The three trigger families

Every n8n workflow starts at a trigger, and choosing the family is an architecture
decision, not a convenience:

**Schedule triggers — the heartbeat.** `Every 60 minutes`, `07:30 daily`. The
autonomy workhorse: it fires *whether or not anyone is watching*, which is the
literal definition of noticing without being asked (Lecture 01). Use schedules for
NOTICE phases and periodic LEARN/REPORT evaluation. The trade-off: latency is
bounded by the interval, never less. Cadence honesty (Lecture 03) applies: state
the configured interval, measure the jitter, never claim real-anything.

**Webhook triggers — the handoff.** `/webhook/cr/triage`. Fires when another system
calls. This is how the scan hands claims to triage without polling, and how the
showcase canvas accepts demo events on demand. The trade-off: webhooks are
on-demand, so they must be **idempotent and authenticated** (below) or you have
built a public write-button.

**Error triggers — the safety net.** Attached to all sibling workflows; fires when
any of them throws (Lecture 08). The only trigger whose job is to be unwanted:
a healthy week produces zero error-trigger executions, and the system is designed
so that outcome is visible and labelled, not silent.

Decision heuristic, compressed: **the world is on a schedule; systems talk to each
other by webhook; failures speak by error trigger.** If you find yourself polling
one n8n workflow from another, reconsider — that's a webhook shape.

## 2. Idempotence: the precondition for scheduling anything

A schedule will re-fire. Distributed components will double-deliver. A webhook will
be retried by a client that never saw your 200. The defining property that makes
all of this safe is **idempotence**: *running the same input twice must produce the
same world-state as running it once.*

For a scan that publishes changes, there is one non-negotiable pattern:
**deduplicate on a content hash, not on a timestamp.**

```
fetch source page
  → sha256(content)                     # hash BEFORE parsing (Lecture 12)
  → if hash in seen.json:               # exact bytes seen before
        emit no_delta; stop             # (a no_delta row is an artifact too!)
  → else:
        write snapshot; record hash; emit event
```

Why hash, not timestamp? A timestamp answers "did the publisher say it changed?" —
trusts the publisher's clock and your fetch path. The hash answers "**did the
evidence change?**" A page can update its "last modified" (hash unchanged → correct
no_delta) or can silently re-serve different bytes (hash changes → correctly
notices). Sources that re-serve identical content with new timestamps are common;
spurious reprocessing cascades from timestamp dedupe are a classic drift-adjacent
failure.

Note the artifact discipline: even the boring outcome leaves a row — `no_delta` in
`seen.json` plus a log line. A scan that ran and noticed nothing must be
indistinguishable in evidentiary terms from a scan that found something: both
leave proof of what they saw.

## 3. Webhook authentication & replay safety

An unauthenticated webhook is a public write-button into your decision pipeline.
Production posture:

1. **Shared secret** at the boundary — header token from env vars, checked in the
   first node; 403 with a receipt if absent (the refusal is itself evidence).
2. **Replay-window nonce** for anything user-triggered (the showcase's demo-in
   webhook): reject duplicates within a window even with a valid token.
3. **Idempotent handler** as the final backstop: same event_id arriving twice →
   second arrival emits a `duplicate_suppressed` row, never a second publish.

The three layers exist because each fails differently: secrets leak, nonces clock-
skew, delivery double-fires. Defense in depth with receipts at each refusal.

## 4. Cadence arithmetic (do it once, in public)

Operational budgets are cadence arithmetic. Suppose a scan of 6 sources at 60-min
cadence, ≈1 actor-unit per source per scan (the declared approximation):

```
per hour:   6 units → 144/day
learn:      every 15 min, ~0 units (reads telemetry)
digest:     07:30 daily, 0 units
nightly:    ≤ 6 publishes budget-capped; tokens: judge calls ≈ 2/scan-with-event
```

Publish the numbers with the cadence (`digest ≤ 4 KB` printed every morning). When
a judge asks "how much does this cost to run," the operator's answer is a table
with mode labels, not a guess. Lecture 23 makes this a full discipline.

## 5. Common mistakes

1. **Timestamp dedupe.** "Skip if last-modified unchanged." The silent re-serve and
   the bumped-timestamp traps both defeat it; hash the bytes.
2. **Unauthenticated webhooks.** Including "internal only" ones — the network is
   never as internal as you think.
3. **Anonymous periodic work.** A 15-min lear-cycle that reads telemetry, finds
   nothing, writes nothing: instrument it anyway (a run_log row), or you cannot
   distinguish "checked and quiet" from "never checked" at 07:30.

## Recap and practice

You can choose trigger families by role, enforce idempotence by content hash with
artifact discipline, and do cadence arithmetic in public.

**Practice:** design the notice phase for your capstone: (a) list sources with
cadence per source; (b) write the dedupe rule as one if-statement; (c) state what
your `no_delta` artifact looks like; (d) defend the interval choice against a
challenge of "make it faster." *(The honest answer costs the cadence arithmetic
from §4 — doubling frequency doubles the unit cost; the sources' own release
cadence sets the floor.)*
