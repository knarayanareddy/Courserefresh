# Calling the world: HTTP, credentials & budgets

**Learning objective.** Configure an HTTP Request node with environment-variable credentials instead of pasted secrets, and set timeouts, retries and per-run caps — with a defined behaviour when a cap is hit.

## 1. The node that talks to everything

The HTTP Request node is the universal adapter — REST APIs (Apify, GitHub, Telegram,
your model provider) all arrive through it. It is also where three operational
sins cluster: pasted secrets, unbounded calls, and infinite retries. This lecture
builds the production posture for all three.

## 2. Credentials: env vars, never pastes

n8n's credential store encrypts secrets and keeps them out of exports — use it.
But between *your laptop/repo* and *the canvas*, the boundary discipline is
environment variables:

```
.env (never committed; .gitignore covers it)
  N8N_API_KEY=…
  APIFY_TOKEN=…
  CR_JUDGE_API_KEY=…
  CR_GH_TOKEN=…

canvas:  the HTTP node references $env / expressions — e.g.
         Authorization: Bearer {{$env.CR_JUDGE_API_KEY}}
```

The rules that keep this honest:

1. **A secret exists in exactly two places:** the env source (a vault, a deploy
   secret, a well-kept `.env`) and the platform's encrypted store. Never in node
   parameters, never in a workflow JSON, never in a receipt.
2. **Names are contracts.** `CR_JUDGE_TOKEN`, `CR_GH_TOKEN` — by-convention tokens
   read from env at runtime. This repo learned the hard way that an
   httpHeaderAuth *credential object* 401s where an env-var token works; the
   env-var pattern is the portable one — record the quirk, don't relitigate it.
3. **Rotate-ability.** Because the canvas references names, rotation is
   re-pointing a name, not editing 40 nodes. Scopes follow least privilege
   (Lecture 17): the GitHub token can write one branch of one repo; the Telegram
   token can post to one chat; the judge token only spends that provider's budget.

## 3. Timeouts and retries: bound every call

Every outbound call gets three knobs set explicitly:

| Knob | Default sin | Production value |
|------|-------------|------------------|
| **Timeout** | none (hang forever) | 30 s (fetches), 120 s (LLM judge — models are slow, not infinite) |
| **Retries** | naive loop / none | ≤ 2 retries, exponential backoff, retry on 5xx/timeout only — **never on 4xx** (a 403 retried is still a 403, just later and louder) |
| **Response code check** | ignored | `onError: continue` + explicit branch: ≥400 → controlled failure path (error receipt, Lecture 08), never a silent null downstream |

The bounded-retry philosophy in one line: **retries buy resilience against
transient noise; they must never become a denial-of-service engine against
yourself.** Three retries with backoff on a 500 is resilience; ten retries on a
403 at 60-second cadence is a self-inflicted incident with a schedule.

## 4. Budgets: the meter in the loop

Paid APIs convert failures into invoices (Lecture 04, Species 3). The posture has
three layers, each checked in a different place:

**1. Per-call caps.** `maxPages` on a crawler, `per_page=5` on a release list,
`max_tokens` on a model call. The response size is bounded *at the request*, before
it can surprise the transform.

**2. Per-run ledger.** Every unit-spending call appends to `token_ledger.jsonl` /
`apify_units.jsonl`: `{ts, kind, units, source, run_id}`. The policy node reads the
running total; the rule is `if budget_exceeded → ESCALATE(over_budget)` — the loop
**stops itself** rather than overdrafting.

**3. The escalation, not a shutdown.** When a cap is hit, the correct behavior is
*escalate to a human with the numbers*, not silently skip work. The digest prints
"budget line: 18.4/25 units, 2 sources skipped pending approval" — the operator
decides whether to raise the cap. A budget that silently swallows the world's
changes is a drift-amplifier (you *think* you're scanning; you're only scanning
what's affordable).

Money is a first-class citizen of the running example on purpose: "1 actor run =
1 apify unit" is an *approximation declared in a config file* and printed on every
receipt (`units_source: approximation`). When better prices are captured, the
number improves — until then it is honestly approximate, labelled as such.

## 5. The call checklist (use it in every lab)

Before any HTTP node ships to production, all eight:
1. Auth via env var / credential, never pasted
2. Timeout set (30 s fetch / 120 s model)
3. Retries ≤ 2, backoff, 5xx-only
4. 4xx routed to the failure path, not retried
5. Response size bounded at the request
6. Every unit appended to the ledger
7. Ledger total checked by the policy before expensive action
8. Error path writes a receipt and stages a digest line

## Recap and practice

You can configure env-var credentials, bound calls in time/size/retries, and wire
per-run budgets with human escalation.

**Practice:** audit one HTTP node you own against the eight-point checklist; for
every miss, name the failure species it invites. Then write the two-line budget
rule for your capstone (`budget_exceeded → ESCALATE`), and say what the digest
prints the morning after it fires.
