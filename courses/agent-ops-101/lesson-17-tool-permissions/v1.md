# Tool permissions & the human exit

**Learning objective.** Write a least-privilege tool permission block for one agent, host-scoped where applicable; name the conditions that must stop the agent and bring in a human — and why consent is one of them.

## 1. Declared scope, not vibes

Everything from Lecture 02 onward has assumed the runtime can refuse. This is the
lecture where refusal gets *declared*. An agent's capabilities are a config, not a
personality:

```json
{ "tool_permissions": {
    "tools": ["http_request", "apify_run_actor"],
    "parameters": {
      "http_request": { "allow": ["docs.n8n.io", "docs.apify.com"] }
    }
  }
}
```

The contract is absolute: **if it is not in the block, it does not exist.** A model
may *ask* for a tool (propose an action that needs it); the runtime refuses
anything outside the declared scope. The block is the difference between an agent
you operate and a process you hope about. And the block is *versioned*: n8n's own
setting surface moved (the `tool_permissions` → `permissions.mode` rename, which
the running case study receipted and its quiz regenerated on) — your permission
model is an artifact with a history, exactly like the rules and the thresholds.

## 2. The three permission models — and the one that's forbidden

| Model | Meaning | Verdict |
|-------|---------|---------|
| **Allowlist** | Only the named tools, only the named hosts, run | The default posture — everything else is a refusal with a reason code |
| **Human exit** | Irreversible-adjacent actions *wait* for a human decision; the wait is visible on the execution | Required for the PA3 tier: assessments, records, deletes, payments |
| **Blanket** | "The agent has all tools; it's smart enough" | **No.** A blanket permission converts the next prompt injection into a data-loss incident (Lecture 04, Species 1). There is no smart enough — there is only declared scope |

Note the subtlety in the allowlist example: `http_request` is **host-scoped** —
`docs.n8n.io` and `docs.apify.com` are allowed; a redirect to
`metrics-collector.example` is a *refusal*, not a fetch. Host scoping matters
because the web's natural behavior is to bounce you places you didn't ask to go,
and exfiltration's favorite shape is "it just followed a redirect."

## 3. Writing the block (the lab exercise, condensed)

Least privilege by subtraction, in order:

1. **Enumerate the agent's jobs.** For the running case study: read sources (actor
   + http), decide (code, in-canvas), write one branch of one repo (github), post
   one message type to one chat (telegram).
2. **Grant one tool per job, scoped to the narrowest parameter set that works.**
   `github` → one repo, one branch (`bot/courserefresh` — the human owns `main`);
   `telegram` → one chat id, templated card only.
3. **Host-scope every fetch-shaped tool.** Allowlist of publisher domains, from
   the same source config the independence model uses — the permission block and
   the source plan are two views of one allowlist.
4. **Never grant** shell/exec, filesystem-wide writes, credential *read* (as
   opposed to *use*), or "all hosts." Each of those crates has a lock on it for
   reasons Lecture 04 catalogued.
5. **Write the refusal paths.** For each tool, what does the system do when the
   ask is out of scope? (ESCALATE / `tool_out_of_scope` + receipt + preserved
   input. A refusal without a receipt is Lecture 08's silence in a permission
   costume.)

The self-test for any block: **"Here is where it refuses."** If you cannot point
at the line, you don't have least privilege — you have a draft. (This is the same
sentence a judge asks for, and the lab grades it literally.)

## 4. The human exit: conditions that stop the world

The stop conditions from Lecture 04, now as *declared, tested config* — with
consent promoted to first-class, because the last lectures of the course depend
on it:

1. **Missing consent.** A learner to be contacted with no consent row → refuse,
   receipt (`consent_missing`), and *the block itself is auditable*: the refusal
   receipt proves the wall held. Consent is a permission on **people**, not just
   data — the symmetric twin of the tool allowlist.
2. **Assessment touched.** Anything that alters what is graded, or records about
   a person → PA3, human-only, with the wait visible on the execution.
3. **Irreversible actions.** Deletes, payments, outbound mail beyond the
   consented templates → human exit.
4. **Out-of-scope tool request.** The runtime refuses; the receipt preserves what
   was requested.
5. **Unknown state.** Missing inputs, failed validation → escalate
   (`unknown_state`), fail closed (Lecture 07's boundary guard).

Design note: the human exit is **visible**, not merely present. "Waiting for
human" appears on the execution, in the receipt stream, and in the digest's
escalation section. An exit nobody can see is an exit nobody takes — and the
queue of waiting escalations is itself an operational metric (Lesson 22's digest
names it).

## 5. Common mistakes

1. **Blanket grants "for the demo."** The demo is exactly when the injection
   specimen arrives. PA3-with-no-exceptions exists because demos create pressure
   to make exceptions; the pressure is the attack.
2. **Key-scoped but not host-scoped.** An `http_request` with a valid credential
   but no host allowlist is a open door with a gold handle: the credential
   proves *you* are allowed, not that *the destination* is.
3. **Silent refusals.** Refusing without receipting is invisible governance —
   indistinguishable from a bug. Every refusal is an artifact.
4. **Confusing consent with notification.** "We told them we'd message them" ≠
   "they said yes." Consent is a recorded, versioned, per-learner row — Lecture
   19 builds the full wall; this lecture's block merely enforces it.

## Recap and practice

You can write a scoped allowlist with refusal paths, and enumerate the five
stop-condition families with consent among them.

**Practice:** write the block for your capstone agent (tools, per-tool parameters,
hosts, branches, chats — writing down the refusal receipt each produces). Then
stress it: what exact sequence would make your agent (a) write to the protected
branch, (b) message a non-consenting human? For each, name the *line* that
refuses. If either sequence has no refusing line, you have found your lab's first
bug — fix the block, not the prompt.
