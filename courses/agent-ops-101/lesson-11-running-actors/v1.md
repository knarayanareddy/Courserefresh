# Running actors from n8n: pinning, waiting, paging

**Learning objective.** Run an actor from n8n and extract its dataset into items; justify pinning a build instead of `latest` with the failure it prevents.

## 1. The junction of the two platforms

The notice phase is a junction: n8n schedules and orchestrates, Apify computes and
extracts. Two integration styles, one rule:

- **Apify node in n8n** (or the OpenAI-tier HTTP call to the Apify API from an HTTP
  node): create run, pass input, **wait for run to finish**, collect dataset as
  output items.
- **Schedule from the n8n side only.** Apify has schedules too, but the decision
  loop should own the clock: cadence lives in one place (your workflow), where the
  budgets and the receipts also live.

The canonical notice block on the canvas:

```
scheduleTrigger (60 min)
  → CODE: SOURCES        emit one item per configured source
  → HTTP/APIFY_RUN_ACTOR run the pinned actor for each source input
  → CODE: NORMALIZE      rows → normalized events (hash, validate required fields)
  → CODE: DEDUPE         seen-hash check (Lecture 06) → event or no_delta
  → HTTP: HTTP_TRIAGE    POST the event to the triage webhook
```

## 2. Pinning: reproducibility or nothing

In production, `build: latest` is a time bomb. The actor you tested against (and
whose output your transforms and quizzes expect) is *some particular build*; the
store's `latest` moves when the actor's author ships. The failure mode is
insidious: your pipeline works for weeks, then an actor update changes the output
shape — adds a `metadata.statusCode` field, renames a key — and your normalize
step throws on unexpected keys at 03:02, every hour, until someone reads the error
receipts (which, thanks to Lecture 08, they *will* read on Thursday).

The pinning discipline:

```json
{ "actorId": "apify~website-content-crawler",
  "build": "0.3.97", "buildId": "u8gClHFAIyDHCQq0J",
  "buildVerified": "D-0", "buildSource": "public actor metadata" }
```

1. **Pin the build number**, recorded beside the pin's verification date and
   source in your source config — the pin is itself an audited fact.
2. **Upgrade deliberately**: bump the pin in a versioned config change, run your
  gold set against a sample fetch (Lecture 21), merge, and let the receipts show
  the migration. The same discipline you apply to any dependency, but for the
  system that feeds your decision loop evidence.
3. **Budget the pin** — actor pricing is per-build; a cheap old build may be a
  reason to stay, *if* its output contract still fits. Deliberate beats floating.

## 3. Wait for run to finish — and bound the wait

Actors are not instant: runs take 30–120 s (Lecture 03's cadence honesty). The
n8n/Apify integration offers "run async" vs "wait for run to finish." **In a notice
phase, wait.** The downstream normalize/dedupe/triage chain assumes the dataset is
complete; async leaves you polling — and a poll loop is a schedule trigger with
extra steps and worse failure modes.

Bounded waiting is part of the contract: sets a timeout in line with Lecture 09
(120 s class), on timeout → error receipt (`fetch_failed`), digest line, retry next
hour on the schedule. Runs that blow past the bound degrade loudly, not silently —
the scan window is an honest number: *source captured → decision made*, printed
with its jitter.

## 4. Paging: the dataset is 1,000 rows per page

Datasets page at 1,000 items. Small crawls never notice; a `maxPages: 5` source
never crosses the boundary. But the day your subject's crawl grows (or you sweep a
docsite for the capstone), the unhandled page boundary manifests as **silent
data loss**: you processed page one, and pages two-to-N never entered the
pipeline. The dedupe hash even makes it *look* like no_delta, since the missing
rows never existed in your world.

The pattern: use the integration's dataset collection (which pages for you), or
when calling the API directly loop `offset`/`limit` until `count < limit`. Assert
the total in the receipt (`rows: 2,417 of 2,417`) so the number is accountable — 
`maxPages` caps *crawl breadth*; paging handles *dataset depth*; and the receipt
records both so "we saw everything we asked for" is checkable.

## 5. Common mistakes

1. **`latest` in production.** The pin exists because output contracts move. (Type
   it into your capstone checklist twice; it is the most commonly skipped line.)
2. **Async runs + hand-rolled polling.** Use wait-to-finish inside the scheduled
   scan; bound the wait; degrade loudly.
3. **Silent page loss.** Loop the pages, assert the total, receipt the count.
4. **Actor output straight into prompts.** The dataset row is untrusted input
   (Lecture 10's trust boundary); it reaches the judge through the sanitise and
   quote-anchoring steps, never raw.

## Recap and practice

You can wire the notice block, pin builds with provenance, bound waits, and page
datasets with asserted totals.

**Practice:** write the notice-block node list for your capstone's *first* source,
then answer the pin question: which actor, which build, where is the build number
recorded, and what breaks when the store updates it — *in your pipeline,
specifically*? Name the node that throws.
