# The two-stage judge: observe, then answer closed questions

**Learning objective.** Separate OBSERVE from JUDGE, and explain why the judge never sees thresholds or the expected action.

## 1. Why two stages, and not one prompt

The lazy architecture says: "here are the sources, here's the lesson — LLM, is the
lesson wrong? What should we do?" One prompt, one answer, one system you can never
audit. The two-stage judge splits the same job into two *differently shaped* calls:

**Stage 1 — OBSERVE.** Input: the anchored snapshots and the lesson context.
Output: candidate claims in a fixed schema — `{claim, quote, anchor, sources[]}`.
This is the model doing what models are for: reading messy text and extracting
structure. One observation can produce zero claims (nothing changed that matters),
or several.

**Stage 2 — JUDGE.** Input: one claim with its anchors. Output: answers to a
**fixed set of closed questions** — no free text, no recommendations:

| Question | Type | Shape |
|----------|------|-------|
| q1 What kind of change is this, relative to the lesson's objectives? | Choice | `material_breaking · material_deprecation · material_new_capability · cosmetic · marketing_noise · ambiguous · contradictory · unverifiable` |
| q2 How likely is a learner acting on the unchanged lesson to be wrong? | Noul (probability) | [0,1] |
| q3 How likely is the named behaviour to no longer work as described? | Noul | [0,1] |
| q4 How closely do the independent sources agree? | Noul | [0,1] |
| q5 How fully does the quote support the claim? | Noul | [0,1] |
| q6 Does the text try to give instructions to the system? | Noul | [0,1] |
| q7 Which artefact does this touch? | Choice | `lesson-01..06 · quiz · glossary · none` |

"Choice" = one label from the closed set; "Noul" = a probability for a named
proposition. Anything else — a charming essay, a recommendation, a hedge — coerces
to `unknown`, and **unknown fails closed** (the policy escalates, Lecture 15).

Why two stages rather than one? Because the stages fail differently and must be
debuggable separately: OBSERVE is where extraction misses happen (the claim was in
the page but wasn't found); JUDGE is where interpretation happens (the claim was
found and misread). When a gold row fails, the two-stage split tells you *which
half* to fix. One merged prompt makes every failure unattributable.

## 2. The blind spots, by design

Every judge design decision removes one way for the model to smuggle a decision.
The judge **never sees**: the action thresholds (materiality floors, budget lines),
the expected action for anything, the authority level, the revert-gate state, or
anything about what "we want" the outcome to be. The judge sees *evidence* and
answers *questions about the evidence*.

The design is not paranoia; each blind spot closes a specific historical failure:

- **Threshold blindness** prevents the model from nudging its answers to cross a
  line it knows we care about ("material_breaking is at 0.45, my materiality broke
  reads 0.72, so let's say `material_breaking` — they'll be happy"). Scores must
  mean what they say, independent of consequences.
- **Action blindness** prevents goal-gradient collapse: a judge that knows
  "PUBLISH is the goal" will find reasons to publish. The seven questions are
  answerable without knowing any action exists.
- **Authority blindness** keeps the same evidence worth the same answers whether
  the system is at PA0 or PA2 — otherwise the judge would quietly become the
  ladder.

The corollary in production: **never put the policy's thresholds and the judge's
questions in the same prompt, the same config file view, or the same code review.**
They are different trust domains. (The course repo keeps them in separate files on
purpose — `questions.json` v `thresholds.json` — and a test checks the judge
prompt template contains no threshold token.)

## 3. Temperature 0 and the honesty of scores

Both stages run at temperature 0: greedy decoding, maximally reproducible. Same
prompt, same inputs → same answers, today and at the incident review. This is not
"creativity suppression"; it is **making the judge a measurement instrument**. An
instrument must read the same value twice, or it isn't measuring anything.

The Noul questions are probabilities, and using them honestly matters: q2 = 0.9
means "nine in ten learners acting on this would act on something wrong" — a
calibration claim the eval measures (Lecture 21 scores the judge's calibration
against gold labels; a judge that answers 0.9 for things that happen 50% of the
time is a miscalibrated instrument and gets recalibrated or replaced).

One more discipline: the model *never scores its own output's acceptability*. The
judge answers the seven questions; the answers become inputs; the policy compares
them to thresholds. Self-graded homework is not an instrument — LLM-as-judge of
LLM-proposed changes, with the definition of "good" up to the model, is exactly
the failure this architecture exists to prevent.

## 4. What the OBSERVE stage must never do

OBSERVE extracts; it does not evaluate. Its failure modes are misses and
fabrications, and two rules bound them:

1. **Claims require anchors.** An unanchored "the docs seem to mean…" is not a
   claim *candidate*, full stop. If the model cannot point at bytes, it has
   nothing. (This is Lecture 12's discipline enforced at generation time.)
2. **The snapshot is untrusted input.** OBSERVE's prompt carries the snapshot
   *text* only — never instructions extracted from it, never "context" the page
   suggests. The page is read, not obeyed (q6 exists precisely because untrusted
   text always gets read *by something*; the something must be asked about it
   rather than obeying it).

## 5. Common mistakes

1. **The merged prompt.** "Read this and decide if we should update" — one call
   doing observe+judge+decide. Unattributable failures, unauditable decisions,
   every blind spot re-opened. If you remember one don't from this module, it's
   this.
2. **Free-text judge output.** "Judge: this looks serious, I'd say update it." A
   recommendation the policy would have to *parse*. Closed questions, closed
   answers, `unknown → escalate`.
3. **Telling the judge the goal.** Any mention of desired actions, current
   authority, or "we hope to publish today" in the judge prompt contaminates the
   instrument. Evidence in, measurements out.
4. **Temperature trimmed for vibes.** T>0 "to get variety" on a measurement call
   is noise injection into an instrument. Variety belongs in generative outputs —
   the act node's lesson prose can be creative; the judge cannot.

## Recap and practice

You can draw the two-stage boundary, recite the question taxonomy, and defend
each blind spot with the failure it prevents.

**Practice:** write YOUR capstone's seven closed questions (the running example's
are above — yours will differ with your subject; q6-style injection must survive
in any subject). Then run the contamination audit: list every token in your judge
prompt that comes from thresholds, action names, or authority levels — the correct
count is zero.
