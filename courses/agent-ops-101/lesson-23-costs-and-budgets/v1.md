# Costs, budgets & the discipline of units

**Learning objective.** Account for a run in the three currencies — tokens, actor units, money (or an explicit unmeasured) — and configure a cap that escalates to a human instead of silently stopping the world.

## 1. The three currencies

An agent run spends in three denominations, and the honest system books all
three:

| Currency | Where it's spent | How the running example books it |
|----------|------------------|-----------------------------------|
| **Tokens** | OBSERVE and JUDGE calls (Lecture 14) | Per-call rows in `token_ledger.jsonl`; nightly total in the digest header |
| **Actor units** | Every pinned-actor fetch (Lecture 11) | `apify_units.jsonl`; units_source declared (`1 run = 1 unit` — an approximation, printed) |
| **Money** | The conversion of the above at real prices | **`unmeasured` until prices are captured** — then a captured price table upgrades the number |

The third row is the lecture in miniature. The euro column stays `unmeasured` in
the running example *on purpose*: prices were not captured into a config file
yet, so the number does not exist — the alternative (a confidently invented
"≈€0.42/run") would be exactly the kind of unreceipted number Lectures 21–22
exist to prohibit. **`unmeasured` is a respectable value.** When prices are
captured, the upgrade is a config change with a version — not a guess promoted
to a fact.

## 2. The ledger, and the approximation rule

Every unit-spending event appends one row — at spend time, not in a nightly
reconciliation:

```
token_ledger.jsonl
{"ts":"…","kind":"observe","model":"…","in":3120,"out":812,"run_id":"cr-…-793","event_id":"cr-n8n-rename-01"}
{"ts":"…","kind":"judge","model":"…","in":1980,"out":64,"run_id":"cr-…-793","event_id":"cr-n8n-rename-01"}
apify_units.jsonl
{"ts":"…","source":"n8n-releases","units":1,"run_id":"cr-…-793"}
```

Two booking rules keep the ledger trustworthy:

1. **Approximations are declared at the unit, not discovered at the total.**
   "1 actor run = 1 unit" is a config-declared approximation (`units_source`),
   printed on every receipt and the digest. Real per-actor pricing varies by
   build and compute; when the approximation grievously misleads, you upgrade the
   unit definition — and the digest's history shows the change, rather than a
   quiet formula swap.
2. **The ledger is append-only and chain-adjacent** — receipts reference their
   ledger rows by run_id; the budget check reads the ledger, never a cached
   counter. A counter can drift from reality; a ledger *is* the reality.

## 3. Cadence arithmetic, revisited with prices

Lecture 06 promised the full cost model. Here it is for the running example
(sim-mode units — labelled):

```
scan:      6 sources × 1 unit × 24 scans/day          = 144 units/day
learn:     telemetry reads only                        ≈ 0
digest:    1/day, no external calls                    = 0
tokens:    ≈ 2 judge calls per scan-with-event         ≈ 100–400k/day at full event load
money:     (units × captured price) + (tokens × captured price) → unmeasured until prices captured
```

The lesson of the arithmetic: **the cadence *is* the budget.** Doubling scan
frequency doubles the dominant line. When someone proposes "scan every 15
minutes," the correct response is not an opinion about freshness — it is this
table plus the freshness actually required by the subject's real change cadence
(n8n and Apify ship weekly-ish; hourly scanning already outruns the subject).
Budget pressure resolves by *reasoning about the subject*, not by enthusiasm
about vigilance.

Cap placement matters as much as cap size: the policy checks the ledger *before*
expensive action (R5's `budget_exceeded → ESCALATE`) — the cap gates the
*decision to spend*, not merely the report of having spent. And escalation is
**not a shutdown**: the run refuses the next spend and hands the human the
numbers ("18.4/25 units, 2 sources skipped pending approval" — Lecture 09's
posture). A budget that silently swallows work is a drift amplifier: you believe
you're scanning all sources; you're scanning the affordable ones.

## 4. When a cap fires in production

The honest escalation sequence, receipted at every step:

```
ledger check → 18.4/25 → R5 clear → proceed
ledger check → 25.2/25 → R5 FIRES → ESCALATE [over_budget]
   · receipt: inputs preserved (which sources were pending)
   · digest line: "budget exceeded; n sources skipped pending approval"
   · human decision: raise the cap (a versioned threshold change) or accept
     reduced coverage (the next digest's scope line shows what the reduction costs)
```

Compare the two cultures this exposes: the *cap-as-safety* culture escalates with
numbers and keeps its coverage visible; the *cap-as-setting* culture treats the
403 as an error to retry around (Lecture 09's self-inflicted incident, now with a
budget). The difference is whether the budget line is * governed * like a policy
rule (versioned, receipted, escalated) or like a YAML number somebody set once.

## 5. Common mistakes

1. **The invented euro.** Publishing a money number no captured price backs.
   `unmeasured` with a named reason is an answer; a guess is a liability.
2. **Nightly reconciliation.** Totalling at 07:30 from logs "when we build the
   digest" — the spend-to-book window is where overruns hide. Append at spend
   time.
3. **Budget as report, not rule.** The budget line printed in the digest but
   checked by nobody: a scoreboard, not a brake. R5 (or your equivalent) must
   gate the spend decision itself.
4. **Scanning the affordable, reporting the intended.** After partial budget
   exhaustion, the digest must name what was skipped — otherwise the coverage
   quietly shrinks while the story stays "we watch everything."

## Recap and practice

You can book the three currencies with declared approximations, do cadence
arithmetic with a subject-driven budget, and wire a cap that escalates with
evidence.

**Practice:** (a) Run your capstone's cadence arithmetic honestly: sources ×
units × scans, token estimate per event, and the *money* line — captured or
unmeasured, never guessed. State the units-source approximation you're declaring.
(b) Your mentor offers unlimited Apify credits for the demo. What changes in your
config, and what must *not* change? *(The cap raises; the ledger, the
approximation labels, and R5's escalation behaviour must not — the discipline is
the artifact, the cap is a number.)* (c) Write the digest line the morning after
your cap fires at 03:00 — refusals-first thinking applies: where does the
over-budget line sit, and what two numbers must it carry?
